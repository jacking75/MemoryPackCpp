# Security and Untrusted Input

A game server deserializes bytes that arrive from clients it does not control.
This document states what the library guarantees against such input, what it does
not, and how to configure it for a hostile network.

For reporting a vulnerability, see [SECURITY.md](../SECURITY.md).

---

## Threat model

**In scope.** `MemoryPackReader` and everything built on it — `Deserialize`,
`TryDeserialize`, the generated object readers, and `PacketFrameParser` — are
designed to be safe when fed arbitrary bytes. Malformed input must produce an
error, never a crash, an out-of-bounds read, or an unbounded allocation.

**Out of scope.**

- `WriteUnmanaged` / `ReadUnmanaged` / `WriteUnmanagedCollection` copy raw struct
  bytes. They are safe against *truncated* input (the length is bounds-checked),
  but they will happily reinterpret arbitrary bytes as your struct. Only use them
  with types whose layout you control, and never with a struct containing
  pointers, indices used unchecked, or anything else that is unsafe to fill with
  attacker-chosen values.
- The library does not authenticate, encrypt, or compress anything. A packet's
  contents are as trustworthy as the transport that delivered them.
- Application-level validation is still yours. A well-formed packet can still say
  "buy 4294967295 items".

## What is enforced

### Bounds checking

Every read goes through a single bounds check before touching memory. The check
is written as `n > size - pos` rather than `pos + n > size`, so it cannot itself
overflow on a 32-bit target — a subtle but real difference on mobile and console
builds.

A failed check either throws or puts the reader into a failed state where all
subsequent reads become no-ops. Either way, no memory outside the input buffer is
ever read.

### Length validation before allocation

This is the attack that matters most for a serializer: a four-byte length field
that asks for gigabytes.

Every collection and string length is validated against the bytes **actually
remaining** before anything is reserved or resized:

```
declared element count  >  remaining bytes / minimum bytes per element   ->  reject
```

So a packet that says "2,147,483,647 elements" but carries no payload is rejected
immediately with `MemoryPackError::LengthLimit`. This applies to `ReadVector`,
`ReadStringVector`, `ReadCollection`, `ReadMap`, `ReadUnorderedMap`,
`ReadUnmanagedCollection`, `ReadArray`, and the string readers.

The unit tests assert this explicitly for every one of those entry points.

### Reserved header values

Object headers in the reserved range 250–254, union headers in 251–254, and
unknown VersionTolerant length markers are rejected rather than reinterpreted.

### Nesting depth

Object readers generated by `MEMORYPACK_DEFINE` track depth, so a deliberately
deep nesting chain cannot exhaust the stack. The default cap is 256.

### Frame reassembly

`PacketFrameParser` enforces a maximum body length (8 MB by default). A frame
that declares more, or declares a negative length, aborts the stream:

```cpp
memorypack::PacketFrameParser parser(64 * 1024);   // this protocol's real maximum
if (!parser.Feed(bytes, onPacket)) {
    closeConnection();   // the stream can no longer be trusted
}
```

## Unmanaged struct padding

`WriteUnmanaged` copies a struct's bytes verbatim, and a struct with natural
alignment has padding between its members. **Those padding bytes go on the wire.**

C++ only guarantees their contents when the object is *value*-initialized:

```cpp
struct Padded { uint8_t tag; int32_t value; };   // 8 bytes: 1 + 3 padding + 4
MEMORYPACK_UNMANAGED(Padded, 8)

Padded a;        // default-initialized: the 3 padding bytes are INDETERMINATE
a.tag = 3; a.value = 0x11223344;

Padded b{};      // value-initialized: the whole object, padding included, is zeroed
b.tag = 3; b.value = 0x11223344;
```

Serializing `a` can emit whatever happened to be on the stack in those three
bytes. Note that default *member* initializers do not help - they initialize
members, not padding:

```cpp
struct Padded { uint8_t tag = 0; int32_t value = 0; };
Padded a;        // members initialized, padding STILL indeterminate
```

Two consequences:

- **Non-reproducible output.** The same logical value can serialize to different
  bytes, which breaks content hashing, deduplication and golden-file tests.
- **Information disclosure.** Up to `sizeof(T) - sum of member sizes` bytes of
  process memory are sent to the peer for every value.

Whether it actually leaks depends on the compiler and optimization level - some
builds zero the padding as a side effect, which is exactly what makes this easy
to miss in testing.

### Rules

1. **Always value-initialize**: `T v{};`, `T v = {};`, a `std::vector<T>` sized
   with `resize()`, or a member with a `{}` initializer. All of these
   zero-initialize padding.
2. Prefer `#pragma pack(1)` layouts (matching C# `[StructLayout(Pack = 1)]`) when
   you control both sides - a packed struct has no padding to leak.
3. If a value passes through a union, `reinterpret_cast`, or a raw buffer, zero
   it explicitly before filling it in.
4. Do not use the unmanaged path for a type where arbitrary bytes would be unsafe
   for the receiver to trust.

The C# side is not affected in the other direction: the CLR zeroes managed
memory, so structs arriving from C# have zeroed padding.

## Configuring limits for your protocol

The defaults bound everything by the input size, which stops the allocation
attack. Tighten them to what your protocol actually uses so implausible packets
are rejected earlier and more cheaply:

```cpp
memorypack::ReaderOptions limits;
limits.maxCollectionLength = 10'000;      // largest legitimate list
limits.maxStringLength     = 64 * 1024;   // largest legitimate string, in bytes
limits.maxDepth            = 16;          // deepest legitimate nesting

memorypack::MemoryPackReader reader(body, limits);
LoginRequest request;
reader.Read(request);
if (reader.Failed()) { dropClient(); return; }
```

A practical server pattern:

| Layer | Limit |
|---|---|
| socket read buffer | a hard cap on bytes buffered per connection |
| `PacketFrameParser` | maximum body length for any packet |
| `ReaderOptions` | maximum collection/string/depth inside a body |
| application | per-packet semantic validation |

## Fuzzing

[`tests/fuzz/fuzz_deserialize.cpp`](../tests/fuzz/fuzz_deserialize.cpp) drives
the whole decoder — objects, nested collections, maps, sets, unions, optionals,
the raw reader API, and the frame parser — with libFuzzer under
AddressSanitizer and UndefinedBehaviorSanitizer.

```bash
clang++ -std=c++23 -g -O1 -Iinclude \
    -fsanitize=fuzzer,address,undefined -fno-sanitize-recover=all \
    tests/fuzz/fuzz_deserialize.cpp -o fuzz_deserialize
./fuzz_deserialize -max_total_time=600
```

There is no hosted CI in this repository, so run it yourself when you touch the
reader — a ten-minute session is enough to shake out an obvious regression. A
crash, a sanitizer report, or an unbounded allocation is a bug.

If you find a crashing input, please attach the reproducer file to your report.

## Hardening checklist for a server

- [ ] Cap bytes buffered per connection, independently of the frame parser.
- [ ] Construct `PacketFrameParser` with your protocol's real maximum body size,
      not the default.
- [ ] Pass a tightened `ReaderOptions` to every reader that touches client data.
- [ ] Drop the connection when `Feed()` returns false or the reader reports an
      error — do not try to resynchronize.
- [ ] Use `TryDeserialize` (or check `reader.Failed()`) rather than letting an
      exception escape into your accept loop.
- [ ] Validate values semantically after a successful decode.
- [ ] Do not use `ReadUnmanaged` for types where arbitrary bytes would be unsafe.
- [ ] Value-initialize (`T v{};`) every unmanaged struct you serialize, so its
      padding cannot carry stack contents onto the wire.
- [ ] Build your server with ASan/UBSan at least in CI.
